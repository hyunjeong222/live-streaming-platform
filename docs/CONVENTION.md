# 협업 컨벤션

이 프로젝트의 브랜치 전략, 커밋 메시지, 이슈·PR, 시험, 기록 규칙이다. 모든 작업은 이 문서를 기준으로 한다.

## 1. 브랜치 전략

```
이슈 만들기 → dev에서 이슈별 브랜치 따기 → 작업 → PR → dev → PR → main

feature/40 ─┐
fix/45     ─┼──► PR (squash merge) ──► dev ──► PR (merge commit) ──► main
docs/60    ─┘                          개발 환경                     운영
```

- 오래 유지하는 브랜치는 `main`(운영)과 `dev`(개발 환경) 두 개다.
- 둘 다 직접 커밋하지 않고, 항상 PR로만 합친다.
- 작업 순서: 이슈를 만들고, `dev`에서 이슈별 브랜치를 따서 작업한 뒤 `dev`로 PR을 보낸다. `dev`에 모인 코드는 따로 PR을 보내 `main`에 합친다.
- 병합 방식: 작업 브랜치 → `dev`는 squash merge로 합쳐 PR 하나가 커밋 하나로 남게 한다. `dev` → `main`은 일반 병합(Create a merge commit)으로 합친다. squash로 합치면 `main`과 `dev`의 이력이 갈라져 다음 반영 때 이미 반영한 커밋이 다시 보이거나 충돌이 난다.
- 브랜치 이름은 `<유형>/<이슈번호>` 형식이다. `#`이나 한글 설명은 붙이지 않는다.

| 브랜치 | 커밋 유형 | 이슈 라벨 | 예 |
|---|---|---|---|
| `feature/` | `Feat` | `type: feat` | `feature/40` |
| `fix/` | `Fix` | `type: bug` | `fix/45` |
| `docs/` | `Docs` | `type: docs` | `docs/60` |
| `refactor/` | `Refactor` | `type: refactor` | `refactor/62` |
| `test/` | `Test` | `type: test` | `test/70` |
| `chore/` | `Chore` | `type: chore` | `chore/71` |
| `design/` | `Design` | `type: design` | `design/72` |

## 2. 커밋 메시지 규칙

```text
<Type>: <제목>

- 변경 내용 1
- 변경 내용 2

Ref: #이슈번호
```

- **유형**: 영어로 쓰고 첫 글자는 대문자다. 아래 중에서 고른다.
  `Feat`, `Fix`, `Docs`, `Style`, `Refactor`, `Test`, `Chore`, `Design`, `Comment`, `Rename`, `Remove`, `!BREAKING CHANGE`, `!HOTFIX`
- **제목**: 한글로 쓴다. 끝에 `.`을 붙이지 않고, 영문 기준 50자 이내로 쓴다.
- **본문**: 한글로, 글머리표(`-`)를 써서 무엇을 왜 바꿨는지 적는다. 파일 목록은 넣지 않는다.
- **꼬리말**: `Ref: #이슈번호`를 쓴다. 이슈가 여러 개면 한 줄에 하나씩 쓴다.
- 제목 끝에 `(#N)`을 직접 쓰지 않는다. squash merge 때 GitHub이 PR 번호를 붙여 준다.
- 성격이 다른 변경(문서, 기능, 시험 등)은 커밋을 나눈다.
- AI 표기(`Co-Authored-By: Claude ...`, `🤖 Generated with ...`)는 커밋과 PR 어디에도 넣지 않는다.

```text
// 좋은 예
Feat: 회원가입 시 이메일 인증 기능 추가

- 인증 코드 발송 API 추가
- 인증 코드 확인 API 추가

Ref: #1

// 나쁜 예
feat: 회원가입 이메일 인증 추가                ← 유형이 소문자
[회원] 이메일 인증 기능 구현 (#51)             ← 대괄호 도메인, 번호 직접 씀
```

## 3. 이슈와 PR

### 이슈

- 이슈는 템플릿(`.github/ISSUE_TEMPLATE`)으로 만든다. 템플릿을 고르면 라벨이 자동으로 붙는다. `gh`로 만들 때도 `--label`로 같은 `type:` 라벨을 붙인다.
- 제목은 `[도메인] 설명` 형식이다. 예: `[member] 로그아웃 후에도 토큰이 동작함`
  - 도메인은 `docs/decisions/README.md`의 폴더 목록과 같다. 설계하면서 정하고, 새 도메인이 생기면 그 목록에 더한다.
  - 특정 도메인에 속하지 않으면 `[common]`, 인프라·설정 작업이면 `[infra]`를 쓴다.
- 이슈 하나에 PR 하나다. 작업이 커지면 이슈를 나눈다.

| 템플릿 | 라벨 | 브랜치 |
|---|---|---|
| ✨ 기능 추가 | `type: feat` | `feature/<번호>` |
| 🐞 버그 제보 | `type: bug` | `fix/<번호>` |
| ♻️ 리팩터링 | `type: refactor` | `refactor/<번호>` |
| 📝 문서 | `type: docs` | `docs/<번호>` |
| ⚙️ 설정·기타 | `type: chore` | `chore/<번호>` |

### PR

- 기준 브랜치는 `dev`다.
- 제목은 커밋 제목과 같은 `<Type>: <제목>` 형식이다. squash merge 때 이 제목이 커밋 제목이 된다.
- 본문은 PR 템플릿(`.github/PULL_REQUEST_TEMPLATE.md`)을 따르고, `Closes #이슈번호`로 이슈를 연결한다. 이슈의 일부만 하는 PR은 `Ref #이슈번호`를 쓴다.
- PR 본문에 AI 표기(`🤖 Generated with ...`)와 "리뷰 요청" 같은 문구를 넣지 않는다. 혼자 쓰는 저장소라 리뷰어는 지정하지 않는다.
- 설계 결정 기록(ADR)이 있으면 `💬 참고 사항`에 저장소 경로를 한 줄 넣는다.
- `dev`로 머지해도 `Closes`로 이슈가 자동으로 닫히지 않는다(기본 브랜치 `main`으로 머지할 때만 닫힌다). 작업이 끝난 이슈는 직접 닫는다.

### PR 전 점검

- push 전에 `./gradlew test`가 통과하는지 확인한다.
- 리뷰어 대신 PR을 올리기 전에 `/code-review`로 `dev` 대비 변경을 점검한다.
- 머지를 막아야 하는 문제(실제로 잘못 동작하는 버그, 보안 문제, 데이터가 깨지는 문제, 이 문서의 규칙 위반)만 고친다.
- 사소한 지적(이름, 스타일, 취향)과 "시험을 더 쓰라"는 제안은 고치지 않고 PR 전에 목록으로만 남긴다.

## 4. 시험

- 커버리지 100%를 목표로 하지 않는다. 주요 흐름과 권한 경우(요청한 사람에 따라 허용·거절이 맞게 되는지)를 확인한다.
- 버그를 고칠 때는 재현 시험을 먼저 만들어 고치기 전 코드에서 실패하는 것을 확인한 뒤 고친다.

## 5. 기록

- **설계 결정 기록(ADR)**: 되돌리기 어렵거나 이유가 코드에 안 보이는 결정은 `docs/decisions/`에 남긴다. 기준과 쓰는 법은 [`docs/decisions/README.md`](decisions/README.md)를 따른다.
- **노션 정리**: 함께 정한 중요한 것들을 노션 프로젝트 페이지 맨 앞의 표에 남긴다. 표 한 행이 문서 하나다. 페이지 위치와 표 열은 `CLAUDE.md`에 적는다.
- 결정 이유는 대화에만 남으므로 `/clear`나 `/compact` 전에 기록 초안을 먼저 확인한다.
- 두 곳 모두 비밀번호, 토큰, 키, 내부 주소, 개인정보를 쓰지 않는다.

## 6. 코드와 설정

- 주석, 커밋 메시지, 문서는 한국어로 쓴다. 클래스·변수·메서드 이름은 영어로 짓는다.
- 엔티티를 추가하거나 고치면 Flyway 마이그레이션을 함께 추가한다. 이미 적용된 마이그레이션은 고치지 않는다.
- `.env`, 비밀번호, 토큰은 커밋하지 않는다. `.env.example`만 올린다.
- 환경변수를 추가하거나 바꾸면 `.env.example`도 같이 고친다.
- Docker 이미지 같은 외부 버전은 `latest` 대신 번호로 고정한다. 로컬(`docker-compose.yml`)과 시험(Testcontainers)은 같은 버전을 쓴다.
