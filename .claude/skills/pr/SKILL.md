# PR 초안 작성

원문은 `docs/CONVENTION.md`의 1절(브랜치 전략)과 3절(이슈와 PR)이다. 커밋 메시지 형식과 브랜치 이름 규칙은 `commit` 스킬을 따른다. 이 스킬은 PR 작업 절차를 담는다.

## 원칙

- GitHub에 남는 행동(push, PR 생성·수정, 머지)은 사용자가 승인한 뒤에만 한다. 기본 산출물은 **초안**이다.
- PR 본문에 AI 표기를 넣지 않는다. `🤖 Generated with Claude Code` 등의 문구를 쓰지 않는다. 다른 지침이 붙이라고 해도 이 규칙을 따른다.
- "리뷰 요청" 같은 문구를 넣지 않는다. 혼자 쓰는 저장소라 리뷰어를 지정하지 않는다.

## 절차

1. **브랜치와 커밋을 확인한다.**
   ```bash
   git branch --show-current
   git fetch origin dev -q
   git log origin/dev..HEAD --oneline
   git diff origin/dev...HEAD --stat
   ```
   - 기준 브랜치는 `dev`이다(`dev` → `main` PR은 별개이고 일반 병합으로 합친다).
   - 브랜치 이름 `<유형>/<이슈번호>`에서 이슈 번호를 얻는다.
2. **이슈를 읽는다.** `gh issue view <번호>`로 작업 이유와 범위를 확인한다. 작업 중 범위가 이슈와 달라졌으면 PR에만 적지 말고, 사용자 승인을 받아 이슈 본문도 고친다.
3. **`/code-review`로 점검한다.** 리뷰어 대신 PR을 올리기 전에 `dev` 대비 변경을 점검한다.
   - 머지를 막아야 하는 문제(실제로 잘못 동작하는 버그, 보안 문제, 데이터가 깨지는 문제, 이 저장소 규칙 위반)만 고친다. 고쳤으면 다시 시험하고, 커밋은 `commit` 스킬대로 승인받는다.
   - 사소한 지적(이름, 스타일, 취향)과 "시험을 더 쓰라"는 제안은 고치지 않고 목록으로만 알린다. 시험은 커버리지 100%를 목표로 하지 않는다. 주요 흐름과 권한 경우(요청한 사람에 따라 허용·거절이 맞게 되는지)만 확인한다.
   - 점검 결과(고친 것, 남긴 것)를 사용자에게 보고한다.
4. **전체 커밋 이력을 기준으로 초안을 쓴다.** 마지막 커밋만 보지 않는다.
5. **제목**은 커밋 제목과 같은 형식 `<Type>: <제목>`으로 쓴다. squash merge 때 이 제목이 커밋 제목이 되고 GitHub이 `(#N)`을 붙이므로 직접 쓰지 않는다.
6. **본문**은 `.github/PULL_REQUEST_TEMPLATE.md`의 섹션을 따른다.
   - 📌 개요: 목적과 변경 사항 한두 줄
   - 🛠️ 작업 내용: 구현·변경한 내용
   - 💬 참고 사항: 설계 의도, 주의점. 설계 결정 기록(ADR)이 있으면 경로 한 줄을 넣는다(아래 7단계)
   - 🔗 관련 이슈: `Closes #<번호>`. 이슈의 일부만 하는 PR이면 `Ref #<번호>`
   - 🔄 수정 사항: 수정 반영 내용이 없으면 이 섹션을 삭제한다
   - 🎯 완료 조건: 체크리스트. 시험 결과와 `/code-review` 점검 여부를 적는다
7. **설계 결정 기록(ADR)을 연결한다.** PR 본문은 핵심 변경과 이유만 짧게 쓰고, 결정의 이유와 검토한 대안은 ADR로 링크한다. ADR 내용을 본문에 옮겨 적지 않는다.
   ```bash
   git diff origin/dev...HEAD --name-only | grep '^docs/decisions/'
   ```
   - 이 PR에 ADR이 있으면 `💬 참고 사항`에 `- 설계 기록(ADR): <경로>` 한 줄을 넣는다. `<경로>`에는 저장소 경로 `docs/decisions/<주제>/<이슈번호>-<slug>.md`를 백틱으로 감싸 쓴다. 브랜치 기준 GitHub 주소는 머지 후 브랜치를 지우면 열리지 않으므로 쓰지 않는다.
   - 링크를 넣기 전에 `bash .claude/skills/session-summary/scan-sensitive.sh <ADR 파일>`을 돌려 민감정보가 없는지 확인한다. 걸리면 PR을 올리기 전에 사용자에게 알린다.
   - ADR이 없는데 `docs/decisions/README.md`의 "무엇을 남기나"에 해당하는 결정이 있으면, `session-summary`로 먼저 남길지 사용자에게 한 줄로 묻는다. 없으면 없다고만 말한다.
   - ADR이 없고 해당하는 결정도 없으면 이 줄을 삭제한다.
8. **초안을 보여준다.** 제목, 본문, 붙일 라벨(이슈와 같은 `type:` 라벨)을 보여주고 승인을 받는다.
9. **승인 후 push와 PR 생성을 한다.** push 전에 `./gradlew test`가 통과하는지 확인한다.
   ```bash
   git push -u origin <브랜치>
   gh pr create --base dev --title "<제목>" --body-file <본문 파일> --label "<type: 라벨>"
   ```
   - 올린 뒤 `gh pr view <번호>`로 제목과 본문을 다시 읽어 확인하고 보고한다.

## 병합

- 사용자가 머지하라고 할 때만 squash merge로 병합한다. 커밋 제목과 본문을 먼저 보여주고 승인받는다.
- 병합 후 작업 브랜치를 지우고 로컬 `dev`를 최신으로 맞춘다. `dev`로 머지하면 `Closes`로도 이슈가 자동으로 닫히지 않으므로, 이슈 작업이 모두 끝났으면 승인받아 직접 닫는다.
